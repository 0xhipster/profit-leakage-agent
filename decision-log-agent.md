# Decision log: agent side

Plain-English record of every technical choice and why. Interview cheat sheet.
Numbers 1 to 16 are in the Power BI decision log. This log continues from 17.

17. Python 3.14 was already installed, so no install was needed.
18. The project lives in its own folder (profit-agent) with a private Python workspace (.venv), so its tools do not mix with anything else on the computer.
19. The agent talks to Claude through the official Anthropic library, directly, not through a framework. This lets us show and explain the whole loop.
20. The API key is stored as a Windows environment variable, never in a file, never in chat, never in GitHub.
21. The first key failed because it was not tied to a workspace. A new key tied to the Default workspace fixed it. The old key was deleted.
22. Haiku is used for testing because it is cheap. The final run uses a stronger model. Costs not yet verified, check Anthropic's pricing page.
23. Test call lesson: Claude miscounted words in a five-word request, then corrected itself. This is why all arithmetic runs as plain code and Claude never calculates.
24. pandas is the library for reading and calculating on tables. It is the standard tool for this job.
25. The load tool only reads and describes the file. It changes nothing. Cleaning is a separate tool, so each tool does one job and can be explained in one sentence.
26. The load tool works on any CSV, not just Global Superstore, so the agent is not hard-coded to one dataset.
27. Load tool check: 51,290 rows and 27 columns, matching the Power BI anchors. Discount has 27 distinct values (decimals preserved), Order.ID 25,035, Market 7.
28. The clean tool does not know this dataset. Claude reads the load summary and tells the tool which columns to drop and which are dates. This keeps the agent reusable on other datasets.
29. The clean tool always drops columns with only one distinct value, since they carry no information (this catches the Chinese-header record-count column).
30. The clean tool works on a copy. The raw table is never changed, so totals can always be reconciled to the source.
31. Duplicates are counted and reported before removal. The check uses the same 9 columns as the Power BI check, so the result (0) is comparable.
32. Clean tool check: after dropping 3 columns, 24 remain. Rows 51,290, Sales 12,642,905, Profit 1,467,457.29, all matching the Power BI anchors. Discount still has 27 distinct values and dates are real dates.
33. The calculate tool groups by one column that Claude chooses, adds up Sales and Profit, then works out margin from the totals. It never averages row margins.
34. The calculate tool prints the exact calculation it ran, so a person can verify every number.
35. The calculate tool checks that the group totals add back to the whole table, and says "DO NOT TRUST THESE NUMBERS" if they do not. This is the reconciliation test built into the tool.
36. Calculate tool check: Category, Market and Year results match the by-hand Power BI tables exactly (rows, sales, profit, margin).
37. The export tool saves tables as CSV files. Power BI reads CSV directly, and it is the simplest format a person can also open and check.
38. The export tool changes no numbers and does no calculation. If a figure in Power BI ever differs from the agent's, the fault is in the calculation, not the export, which makes problems easier to trace.
39. After saving, the export tool reads the file back and compares it with the table: row count, column names, and every value in every number column. It says "DO NOT TRUST THIS FILE" if anything differs. This is the same idea as the reconciliation check in the calculate tool.
40. The export tool only accepts file names made of letters, digits, underscores and hyphens, and always saves inside the output folder. This stops Claude from writing a file anywhere else on the computer by mistake.
41. All exported files go in a folder called output inside profit-agent. The raw superstore.csv is never touched.
42. Export tool check: Category table exported, the read-back check said YES, a bad file name was refused, and the saved file shows the same rows, sales and profit as the Power BI benchmark (Furniture 4,110,884 and 285,204.72; Office Supplies 3,787,330 and 518,473.83; Technology 4,744,691 and 663,778.73). The file stores full precision (for example 285204.7238), so round only when displaying.
43. Charts are drawn with matplotlib. It is the standard Python charting library, runs on the computer with no outside service, and saves PNG pictures that go straight into the PDF brief.
44. The chart tool uses one fixed template: bars sorted with the highest at the top, all gray except one highlighted blue bar, the value written at the end of each bar, no gridlines, no legend, one font, a conclusion-style title, a subtitle saying what is measured, and a source line. Claude chooses the table, the columns, the highlighted bar and the wording. The code does all the drawing, so every chart looks the same.
45. The chart tool takes its values straight from a table that another tool produced. Nothing is retyped or recalculated. It refuses a chart with missing values, duplicate labels, fewer than 2 or more than 15 bars, or an unknown highlight, and it lists every plotted value in its summary so Claude (which cannot see the picture) and a person can check the title against the numbers. The tool cannot judge whether a title is true, so the final check must compare each title with the plotted values.
46. Chart review changes after the first draft: the gray was darkened because the first gray looked too light, and the highlighted bar's number stays bold on purpose so the eye lands on it. The source line on the margin chart drops "currency units not verified" because a percentage has no currency. Charts showing sales or profit amounts may need that note back.

Bug found on the first rerun: saving the chart crashed with "Invalid argument" because the old picture was probably still open in a viewer (Windows will not overwrite a file that is open elsewhere; this was not confirmed, but closing the picture fixed it). The chart and export tools now catch a failed save and say in plain words to close the file and run again. This matters because the agent saves files on every run, so a leftover open picture must not cause a confusing crash.
48. The calculate tool can group a number column into bands. Claude gives a list of cutoffs and the code makes the bands. Each cutoff belongs to the band below it, and the band edges are written in the result. This keeps the tool generic: Claude chooses the cutoffs, so nothing about the 20% line is hard-coded.
49. Check of the bands: cutoffs 0 and 0.2 reproduce the Power BI Discount Band table exactly (None 29,009 rows, 25.32%; Low 10,953 rows, 13.75%; High 11,328 rows, -42.21%).
50. The calculate tool also counts loss rows (rows where Profit is below 0) in every group. The three bands give 0, 2,364 and 10,180, which add up to the benchmark total of 12,544. This is what lets the agent reproduce the "89.9% of High band rows lose money" figure.
51. The agent loop is written directly on the Anthropic library, no framework. Each round Claude either asks for a tool or writes its final answer. The code runs the tool and sends the text result back. This repeats until Claude finishes or the step cap is reached.
52. Claude only knows the tools through the short descriptions we write, so the descriptions say what each tool does, what to give it and what comes back. A vague description would make Claude guess, for example which columns to drop.
53. The instructions are a ten rule brief. The core rules: Claude never calculates (rule 1), every number in the findings must appear in a tool result including numbers from memory (rule 2), reconciliation lines are checked, "associated with" never "caused by", a question whose claim the data contradicts is challenged, and a cutoff chosen after looking at the data is declared. The brief names no columns, so it works on any dataset.
54. Rules 1 and 2 are separate on purpose. Rule 1 stops wrong maths. Rule 2 stops invented numbers of any kind, such as "better than most competitors".
55. Step cap: 15 rounds. At the cap the tools are switched off and Claude must write its findings from what it has and list what it did not check, so every run ends with an answer. The cap protects against cost and against endless drill-downs.
56. Tables are kept in the program's memory by name (raw, clean, result_1, result_2 and so on). Claude refers to tables by name and never passes numbers around, so a number cannot be altered between tools.
57. If Claude asks for something invalid, the error goes back to it as plain text and it can try again. The run does not crash.
58. Every run prints each tool call and result, and saves the same text to output/run_<date>_<time>.txt, so any number in the findings can be traced to a tool result. Each run also reports how many tokens it used.

78. New option ratio_of [numerator, denominator] with cutoffs or bin_width. It divides one column by another per row, then bands the result. Shipping cost divided by sales is the example, but any two number columns work. A ratio with no bands is refused, because a ratio is different in almost every row and would give thousands of groups.
79. Rows where the denominator is 0 or missing have no ratio. They are kept in their own group called "undefined (denominator is 0 or missing)", never dropped, and the summary says how many there are. Here it is the one line item with Sales of 0 (profit -1.11). Dropping it would make the reconciliation fail by one row, and the tool would say DO NOT TRUST.
80. New option bin_width gives equal-width bins that include the lower edge and exclude the upper edge (0.05 gives 0 to under 0.05, 0.05 to under 0.1). This matches the Power BI bin group used for the by-hand table. The cutoffs option keeps its different rule (each cutoff belongs to the band below), because that is what the discount band benchmark uses. Both rules are written into the tool descriptions.
81. Ratios are rounded to 6 decimals before binning. Reason: 256 rows have a ratio sitting on a bin edge (for example exactly 0.15), and a computer may store 0.15 / 0.05 as 2.9999999999999996, which puts the row in the wrong bin. Without rounding, the first bin had 7,220 rows against 7,183 in Power BI, and other bins were off too. I tried several rounding levels against the benchmark: 5 and 6 decimals reproduced all 13 row counts exactly, 4 or fewer decimals did not. I chose 6. Honest limit: this rule was fitted to match Power BI, so it is evidence that both programs treat edge values the same way, not proof of how Power BI works inside.

New option filters on the calculate tool: a list of conditions, each a column plus exactly one of equals (a value), above (a number, strictly greater) or at_most (a number, less than or equal); all conditions must hold.
